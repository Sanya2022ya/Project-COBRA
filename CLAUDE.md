# COBRA — Cache with Optimized Budget and Resource Arbitration

КОБРА — Кэш с Общим Бюджетом и Ресурсным Арбитражем.
Магистерская работа (РГРТУ, кафедра ЭВМ). Автор — Бобычев А. Г., научный руководитель — Дьяков С. Н.

Подробности: `docs/concept.md` (проблема, модель, формулы, аналоги), `docs/roadmap.md` (этапы и задачи).

## Суть

Встроенный (in-process) кэш для Java-приложений. Заменяет «зоопарк» независимых кэшей одним пулом,
разделённым на **регионы** (бывшие отдельные кэши: тарифы, лицевые счета, отчёты…).
**Арбитр** периодически перераспределяет общий бюджет памяти между регионами по **стоимости промахов**
(сколько времени хранилища экономит следующий мегабайт), а не по числу попаданий.
Плюс **защита кучи**: при нехватке памяти у приложения общий бюджет кэша сжимается.

Цель — меньшая суммарная нагрузка на хранилище при том же объёме памяти и отсутствие OOM.
Hit Ratio при этом может быть ниже — это осознанный размен.

## Ключевые понятия

| Термин | Смысл |
|---|---|
| Регион (`Region`) | логическая группа данных со своей долей памяти, своим хранилищем и вытеснением (LRU) |
| Бюджет | общий лимит памяти в **байтах**; доли регионов в сумме ≤ бюджета |
| `Weigher` | оценка размера объекта в байтах |
| `Ticker` | источник времени (виртуальный в симуляторе, `System.nanoTime` в демо) |
| λᵢ | интенсивность запросов к региону (EWMA) |
| cᵢ | средняя стоимость промаха региона — время выполнения загрузчика (EWMA) |
| Теневой список | ключи (без значений) недавно вытесненных объектов; попадание в него = «было бы попадание при +Δ байт» |
| Хвост LRU | самые старые Δ байт региона; попадания в него = «потеряли бы при −Δ байт» |
| gainᵢ / lossᵢ | λᵢ·cᵢ·ĥ⁺ᵢ и λᵢ·cᵢ·ĥ⁻ᵢ — выгода/потеря от ±Δ байт |
| Стратегия (`AllocationStrategy`) | правило, как делить бюджет между регионами |
| Арбитр КОБРЫ | стратегия: переносит Δ от региона с min loss к региону с max gain, если gain > loss·(1+ε) |
| Защита кучи | AIMD: давление после GC → бюджет ×β; нет давления → бюджет +шаг |

## Архитектурные правила (не нарушать без обсуждения с автором)

1. **Ядро не знает, где запущено.** Время — только через `Ticker`. В `cobra-core` нет прямых вызовов `System.nanoTime()` / `currentTimeMillis()`.
2. **Стоимость промаха измеряет ядро** — по времени выполнения загрузчика через `Ticker`. В симуляторе загрузчик «тратит» стоимость из профиля, сдвигая виртуальные часы.
3. **Стратегия — сменный модуль.** Арбитр КОБРЫ — одна из реализаций `AllocationStrategy`. В симуляторе у всех стратегий одинаковые хранилище и вытеснение внутри региона — меняется только распределение памяти (контролируемый эксперимент).
4. **Бюджет считается в байтах, распределяется по стоимости.** Не смешивать (не кодировать стоимость в вес объекта).
5. **В демо альтернативы — реальные продукты** (Caffeine, Redis) за общим фасадом; стоимость промахов меряется на фасаде одинаково для всех режимов.
6. **Прототип: простота важнее скорости.** Блокировка на регион и коллекции JDK допустимы.

## Правила работы

- Автор — студент; он должен понимать и уметь защитить **каждую строку**. Поэтому:
  - задачи маленькие (1–3 часа), перед кодом — короткий план, после — объяснение ключевых решений;
  - научная суть (оценщик выгоды, арбитр, защита кучи, расчёт оптимума) — **сначала обсуждение формул и псевдокода, потом код**, никогда не реализовывать «молча».
- Каждая задача — код + тесты (JUnit 5); `mvn -q verify` должен проходить.
- Новые зависимости — только с согласия автора; в `cobra-core` — никаких.
- Идентификаторы — на английском; комментарии, Javadoc и сообщения коммитов — на русском.
- После задачи отметить её в `docs/roadmap.md`.
- **Не подгонять результаты.** Слабый или отрицательный выигрыш в эксперименте — тоже результат, фиксируем как есть.
